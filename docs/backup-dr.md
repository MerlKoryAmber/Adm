# Бэкап и восстановление (DR) — admanager

Дата: 2026-09-25 МСК. Относится к ADR-0006 (шифрование секретов, envelope).

## Что бэкапить

Состояние admanager — это **две независимые части**, и для восстановления нужны **обе**:

1. **База данных `AdManager`** (SQL Server / Express). Хранит: RBAC (роли, scope, назначения), настройки (SMTP, HTTPS, operational identity), автоматизации, шаблоны форм, аудит. Секреты в БД лежат **зашифрованными** (envelope, AES-256-GCM).
2. **Ключ шифрования (keyring)** — файл `key.dat` в каталоге keyring. По умолчанию `C:\ProgramData\AdManager\keyring\` (переопределяется `ADMGR_KEYRING`). Файл сам защищён DPAPI machine-scope. **Без этого ключа секреты из бэкапа БД не расшифровать.**

> Ключ и БД бэкапить и хранить **раздельно**. Если оба лежат в одном бэкапе — теряется смысл разделения (компрометация бэкапа = компрометация секретов).

## Бэкап

### 1. База данных
Регулярный бэкап средствами SQL Server (пример — ежедневно):
```powershell
sqlcmd -S .\SQLEXPRESS -Q "BACKUP DATABASE [AdManager] TO DISK='D:\Backups\AdManager.bak' WITH INIT, COMPRESSION"
```
Хранить по своей политике ретенции. Для прод-SQL — штатный план обслуживания.

### 2. Ключ шифрования
Скопировать файл ключа в защищённое хранилище, **отдельно** от бэкапа БД:
```powershell
Copy-Item "C:\ProgramData\AdManager\keyring\key.dat" "\\secure-share\admanager-keys\key.dat"
```
Сверить, что бэкап соответствует текущему ключу, можно по **отпечатку** в UI: Settings → Secret encryption → Key fingerprint. Тот же отпечаток = тот же ключ.

> Важно: `key.dat` зашифрован DPAPI **machine-scope** исходного хоста. На другом хосте DPAPI его не расшифрует напрямую — для переноса см. раздел «Перенос на другой хост».

## Восстановление (DR)

### Тот же хост
1. Восстановить БД из `.bak`:
   ```powershell
   sqlcmd -S .\SQLEXPRESS -Q "RESTORE DATABASE [AdManager] FROM DISK='D:\Backups\AdManager.bak' WITH REPLACE"
   ```
2. Убедиться, что `key.dat` на месте (`C:\ProgramData\AdManager\keyring\`). Если пропал — вернуть из бэкапа ключа.
3. Запустить сайт. Секреты читаются, отпечаток ключа в Settings совпадает с ожидаемым.

### Перенос на другой хост
DPAPI machine-scope привязан к машине, поэтому просто скопировать `key.dat` на новый хост **недостаточно** — новый DPAPI его не прочитает. Порядок:
1. Восстановить БД на новом хосте.
2. Перенести **сам AES-ключ** (не DPAPI-обёртку). Способ — экспорт/импорт ключа:
   - На старом хосте ключ доступен приложению (DPAPI расшифровывает). Плановый способ переноса — **ротация на новом хосте после ручного ввода секретов** (см. ниже), либо экспорт ключа административным инструментом (если добавлен).
3. Если исходный ключ на новый хост перенести не удаётся — восстановить БД, затем **ввести секреты заново** в UI (Settings): SMTP-пароль, PFX-пароль, пароль operational identity. Данные (роли, аудит, настройки) при этом **не теряются** — теряются только зашифрованные секретные поля, которые вводятся повторно.

## Ротация ключа

UI: Settings → Secret encryption → **Rotate encryption key**. Действие:
1. Читает секреты старым ключом.
2. Генерирует новый ключ (старый перестаёт использоваться).
3. Пере-шифровывает все секреты в БД новым ключом.

После ротации — **сделать свежий бэкап ключа** (старый бэкап больше не подходит; сверить по новому отпечатку).

## Потеря ключа

Если `key.dat` потерян и бэкапа ключа нет:
- Данные БД (роли, scope, назначения, аудит, несекретные настройки) **сохранны**.
- Зашифрованные секреты (SMTP/PFX/op-identity пароли) прочитать нельзя — **ввести заново** в Settings.
- После ввода приложение сгенерирует/использует текущий ключ и зашифрует секреты снова.

## Проверка бэкапа (рекомендуется периодически)
1. Развернуть БД из бэкапа на тестовом хосте.
2. Положить ключ (или ввести секреты заново).
3. Открыть Settings — секреты читаются, отпечаток ключа совпадает.
